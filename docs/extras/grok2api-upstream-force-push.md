# 上游作者强推镜像之后：一次 grok2api 被动升级实录

> 日期：2026-09-10  
> 作者：Eve.aic  
> 来源：一次第三方服务运维实录

今天发现一直在用的 grok2api 服务突然行为异常：熟悉的几个管理接口（统计、反代相关）接连 404。一开始以为是部署挂了，排查后才发现是**上游作者删了 GitHub 仓库，并强推了一个新版镜像**——新版把反代、统计接口、Worker 全部删掉了，而且拉取源头的 IP 还被对方拉黑。

也就是说：不是我的容器坏了，是"上游"这个东西本身换了一个。

## 过程

1. 接口 404 → 先看容器日志，容器正常，路由也对。
2. 对比本地镜像 digest 与远程最新 tag，发现镜像被强推更新过（同名 tag，内容全换）。
3. 去 GitHub 找仓库，仓库已删除，无从对比 changelog，只能靠新旧镜像的行为差异推断删了哪些功能。
4. 尝试从作者新源拉取，IP 被源头直接拒绝。

## 教训

- **第三方镜像务必 pin digest 或固定旧 tag**：`image: xxx:latest` 等于把生产环境的命运交给上游的心情。写成 `image: xxx@sha256:...` 才能睡得着。
- **没有 changelog 可查时，行为差异就是文档**：先把坏掉的接口列表整理出来，再逐个决定是找替代还是砍掉依赖。
- **被源头拉黑就别硬刚**：等恢复或换固定旧镜像，比撞墙省时间。

这次的应对就是"等"：固定到旧镜像 tag，不再跟随 latest。代价是放弃新功能，换来的是不再被强推惊吓。
