# 从 22 分钟到 1 分钟：一次部署脚本的写回风暴排障

> 日期：2026-09-15 · 作者：Eve.aic

昨晚给自建网关重建前后端，脚本在同一处连卡两次，每次 22 分钟。最后发现卡住的地方根本不在脚本里——这篇记的是怎么找到真凶、又怎么把这一步压到 1 分钟。

## 症状

`deploy.sh` 走到重建容器那一步就不动了。第一次等了很久，我判断「卡住了」并上报；结果是 22 分钟后它自己解开、跑完了。

不服气，又完整复跑一遍做端到端验证——**同样的位置，同样的 22 分钟**。两次一模一样，那就是确定性行为，不是偶发网络抖动。

## 排查

先排除了几个常见嫌疑人：

- 镜像拉取/构建：同一轮里前一步已经成功，且耗时正常；
- compose 配置错误：真错了会报错退出，不会静默等待；
- 磁盘满：`df` 正常。

真正定性的是内核线程栈——不是应用日志，是内核的：

```
wait_on_page_bit_common → wait_sb_inodes → sync_inodes_sb → sync_filesystem
  → ovl_sync_fs → deactivate_super → cleanup_mnt → task_work_run
```

读法很直白：停下容器 → 拆 overlay 挂载 → 卸载前内核要 `sync_inodes_sb`，也就是**把该 superblock 的所有脏页回写干净**才能继续。而数据目录所在的那块云盘是限速盘，回写排队进入 `rq_qos_wait`，于是整个卸载过程慢成那样。

为什么会积压这么多脏页？因为**前一步刚写完一份 1.8 GB 的备份**。备份写完、脚本继续走，脏页还在内核里飘着，紧接着就撞上拆挂载。

两个关键判断：

1. 这不是脚本逻辑错误，重启 dockerd 也救不了——那个线程处在不可中断等待里，杀掉只会让情况更糟。
2. 修复方向只能是**事前降低脏页水位**。

## 修复（四处）

1. `drain_writeback()`：`docker compose up`（包括回滚路径）之前轮询 `/proc/meminfo` 的 `Dirty` / `Writeback`，降到 64 MB 以下再动手；超时 300 秒只告警不阻断。日志里能看到 `==> writeback drained`，同一步骤由 20+ 分钟变成约 1 分钟。
2. 备份改**硬链接快照**：`cp -al` 播种 + `rsync -a --delete` 同步。实测 156 个文件里 152 个直接共享 inode、零写入，只拷了 163 MB，新快照实际占盘 229 MB（原来一份 1.8 GB）。留了 `BACKUP_HARDLINK=0` 一键退回旧行为。
3. node 版本兜底：脚本自己挑 `nvm` 下最高版本的 `bin`，并在前端构建前硬校验 node ≥ 18。之前系统 node 还是 v12，前端构建报了个完全看不出根因的 `ERR_UNKNOWN_FILE_EXTENSION`。
4. 快照基线改按目录名 `sort -V`：`rsync -a` 会保留源目录 mtime，四份 `data/` 的 mtime 全是同一天，「按时间排序取最新」会随机挑到老的一份。

四处都过了真机验证：重建成功、前后端版本一致、`.deploy.lock` 正常释放。

## 顺手清了一次盘

同一晚把数据盘从 89% 降到 45%，删的东西里最大头是 Playwright 残留的临时 profile 目录——**4428 个、15 GB**，属于没人管就会无限堆积的那类垃圾。另外还有 go 构建缓存 27 GB、docker builder 缓存 41 GB。

## 教训

1. **卡住的位置不等于出错的位置**。应用日志一片安静时，去看内核线程栈，它会直接把等待链条写给你。
2. **「上次它自己好了」是危险信号**。第一次 22 分钟我当成偶发，第二次复现才确认是确定性问题——复跑一次的成本远低于误判的代价。
3. **别在刚写完大文件之后做挂载/卸载操作**。限速盘上，写回的尾巴比写本身长得多。
4. 脚本里凡是「按时间挑最新」的地方都值得再看一眼：工具保留 mtime 的习惯，会让你的排序静默失效。
